# 0009. Throttle `get_trip_by_invite_code` and `join_trip` inside Postgres, not just at the edge

Status: accepted
Date: 2026-09-19

## Context

`docs/security-review-2026-09-17.md` found `get_trip_by_invite_code` and
`join_trip` guessable/joinable with no rate limiting at all (invite codes
are 8 hex chars, ~32 bits, generated by `md5(random())`). The first fix
(`src/lib/rate-limit.ts`, `src/app/api/trip-invite/[code]/route.ts`,
`src/app/api/join/route.ts`) added a per-IP Upstash-backed sliding-window
limiter in front of new Next.js routes, and moved `/join/[code]/page.tsx`
off calling `get_trip_by_invite_code` straight from the browser.

`docs/security-review-2026-09-17-followup.md` (finding #1) verified live
that this didn't close the original finding: `get_trip_by_invite_code` is
still `grant`ed to `anon`, `join_trip` to `authenticated`
(`supabase/migrations/0002_fix_function_grants.sql`), and both are
directly callable against Supabase's own PostgREST endpoint with the
public `NEXT_PUBLIC_SUPABASE_*` key — no code changes required, just
skip `splitiful.app` entirely. Vercel's edge, where the app-level limiter
runs, is never in that request's path. `docs/ROADMAP.md`'s
invite-code-rpc-hardening entry named two remediation options and
deferred the choice to whoever picked this up.

## Decision

Add the throttle inside the `plpgsql` functions themselves
(`supabase/migrations/0013_throttle_invite_rpcs_in_postgres.sql`) — the
one layer every call path, app-routed or direct, actually passes through.
A new `public.rpc_rate_limits` table (no grants to `anon`/`authenticated`,
RLS enabled with no policies, so it's unreachable via PostgREST even by
mistake) backs a shared `public.throttle_rpc(_bucket_key, _limit,
_window_seconds)` helper that raises once a bucket's fixed-window count
is exceeded. Both RPCs call it before doing any real work:

- `get_trip_by_invite_code` (still `anon`-callable, by design — the
  zero-auth invite-link preview from `docs/features/simplified-onboarding`
  stays zero-auth) keys the bucket on `x-forwarded-for`, read from
  PostgREST's `request.headers` GUC via
  `current_setting('request.headers', true)::json ->> 'x-forwarded-for'`.
- `join_trip` (still `authenticated`-only) keys the bucket on
  `auth.uid()` — a JWT-verified identity, not a client-supplied value.

Route handlers now translate the DB-raised `'rate limited: try again
shortly'` exception into the same 429 shape `enforceRateLimit` already
returns, via `isDbRateLimitError`/`dbRateLimitResponse` in
`src/lib/rate-limit.ts`.

## Alternatives considered

- **(a) Revoke the `anon`/`authenticated` grants and route all access
  through a service-role server-only client.** This was the follow-up
  report's other named option, and it's the cleaner fix *for
  `get_trip_by_invite_code`* in isolation — that function has no
  per-caller identity dependency, so swapping its grant for a narrowly-
  scoped `SUPABASE_SERVICE_ROLE_KEY` call from
  `src/app/api/trip-invite/[code]/route.ts` would fully close the direct-
  call path with no header-trust caveat at all.

  Rejected as the fix for *`join_trip`*, though, which is the more
  security-sensitive of the two (it creates a `trip_members` row): its
  verification guard (migration 0010, `coalesce((auth.jwt() ->>
  'is_anonymous')::boolean, false)`) and its `auth.uid()`-keyed insert
  both depend on the *caller's own* JWT being present in the request —
  that's what makes the function know who's joining and whether they've
  confirmed their email. A service-role call carries no user JWT by
  default, so this app's own server route would need to independently
  re-verify the session (already doable, since it has the session cookie)
  and pass the user id as an explicit parameter — at which point
  `join_trip`'s signature and trust model have changed, not just its
  grant. Worse, `authenticated` isn't an app-specific credential the way
  a service-role key is: any legitimately signed-in Supabase user,
  whether they got there via this app's UI or a hand-rolled client, holds
  the exact same `authenticated` role and JWT. Revoking `authenticated`'s
  grant wouldn't distinguish "our app calling on a user's behalf" from
  "that same user calling directly" — it would just break the feature for
  everyone, including this app, since both paths are identical at the
  grant level. Rather than split the two functions across two different
  remediation strategies (service-role for one, DB-side throttle for the
  other) and take on a new, highly sensitive credential
  (`SUPABASE_SERVICE_ROLE_KEY` bypasses RLS entirely) for only half the
  win, both functions use the same mechanism.
- **Do nothing until this can be verified against a live deployment.**
  Rejected — the direct-to-Supabase path has *zero* throttling today, not
  "the same imperfect throttling the app path gets" (see follow-up
  finding #1's literal framing). Shipping the DB-side throttle now is a
  real improvement over that baseline even before live verification;
  re-verifying it live is called out below as a required follow-up, not a
  precondition for landing the code.

## Post-acceptance correction (2026-09-19)

The first version of this migration shipped with a genuine bug, not just a
theoretical risk: `throttle_rpc`'s `on conflict (bucket_key) do update set`
referenced `window_start`/`attempt_count` unqualified in its `case`
expressions. Postgres rejects that as ambiguous — an upsert's `excluded`
pseudo-relation shares the insert's target-list column names, so a bare
reference to a column both `excluded` and the target row have doesn't
resolve to either — and it fails on the *first* call, not just on an actual
conflict. Since `throttle_rpc` is the first statement in both
`get_trip_by_invite_code` and `join_trip`, this would have made both RPCs
100% non-functional (a full outage of invite preview and joining a trip)
had it been applied to a live database. The migration file's own
"prove the SQL never actually ran" caveat (see the QA test's header
comment) is exactly why this wasn't caught before landing: `npm test`,
lint, typecheck, and build were all green, because nothing in that suite
executed the SQL. Caught by a QA pass that built a throwaway local
Postgres 10 instance (`initdb`/`pg_ctl`) and called the RPCs live, and
independently re-verified the same way before the fix below was pushed.

Fixed by table-qualifying every reference inside the `do update set`
(`rpc_rate_limits.window_start`, `rpc_rate_limits.attempt_count`) — verified
live: 20 calls succeed under the `limit=20` bucket, the 21st correctly
raises `rate limited: try again shortly`, and a rejected call leaves no
partial state (the whole statement, including `throttle_rpc`'s own
insert/update, rolls back together). The `x-forwarded-for` extraction was
also hardened at the same time to guard `request.headers` being the
literal empty string (not just unset) before the `::json` cast, per a
lower-severity finding from the same QA pass.

This migration was never applied to any live Supabase project before the
fix (no CD pipeline runs migrations automatically — see `docs/ROADMAP.md`),
so this was corrected in place in the same file rather than as a follow-up
migration; nothing had to be un-applied.

## Consequences

- Both RPCs are now throttled the same way regardless of caller — this
  app's own routes, a script hitting Supabase directly with the public
  key, or (for `join_trip`) a script that's minted its own anonymous
  session. The core gap finding #1 described — "a Vercel/Next.js-side
  rate limiter cannot protect a Postgres function that's independently
  public" — no longer applies, because the throttle isn't a
  Vercel/Next.js-side mechanism anymore.
- **Watch for**: `get_trip_by_invite_code`'s `x-forwarded-for` trust
  assumption carries the exact same caveat
  `docs/security-review-2026-09-17-followup.md` finding #3 raised for
  `src/lib/rate-limit.ts`'s app-level limiter, just relocated — if
  whatever sits in front of Supabase's PostgREST endpoint ever *appends*
  to an inbound client-supplied `X-Forwarded-For` instead of overwriting
  it, a caller gets a fresh bucket every request just by sending a
  different fake first hop, no proxy infrastructure required. This
  hasn't been (and, from this repo, can't be) verified live — same
  limitation the original follow-up report hit trying to verify Vercel's
  equivalent behavior before the feature was deployed. **Must be
  re-verified once this migration is live**, the same way finding #3
  recommended for the app-level limiter: send a distinct forged
  `X-Forwarded-For` per request and confirm the limiter still triggers
  after N requests.
- `join_trip`'s `auth.uid()`-keyed throttle has no such caveat — it's
  keyed on a cryptographically-verified value, not a client-suppliable
  header — but it only raises the cost of guessing (mint a new anonymous
  session per N attempts), the same "slower, not impractical" ceiling
  finding #2 already named for the app-level limiter. `invite_code`
  length/format itself remains explicitly out of scope (per the original
  report's decision, reaffirmed in `docs/ROADMAP.md`).
- `public.rpc_rate_limits` grows one row per distinct bucket key
  (IP or user id) and is never pruned by this migration. Low-volume
  enough not to matter yet for this app's traffic, but a future cleanup
  (a scheduled `delete ... where window_start < now() - interval '1
  day'`, or `pg_cron` if it's ever enabled) should land before this
  table's size becomes its own operational concern.
- This does not touch `get_trip_summary`'s separate, still-open
  unthrottled-RPC gap (`docs/ROADMAP.md`'s "also should-fix, not yet
  actioned" note) — that function returns `invite_code` and is still
  called directly from the browser, same class of issue, deliberately
  out of scope for this change.
