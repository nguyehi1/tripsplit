# Security constraints: expense-delete-and-polish (requirements mode)

Date: 2026-10-19. Reviewed: requirements.md, planning.md, security-baseline.md, migrations 0001, 0005, 0006, 0014, 0015, 0016, 0018, ARCHITECTURE.md.
Attacker model: free anonymous account that is a verified member of a trip (or a member of the same trip as a victim).

## Positions

**paid_by vs creator.** Use `paid_by = auth.uid()` as "creator" (matches edit rule, ADR 0002). Accept, with one hardening: the insert policy lets a direct API call create an expense with `paid_by` = another member (policy only checks that paid_by is a member). That lets an attacker plant an expense owed to a victim that the victim can then delete, and, worse, one the attacker (not the payer) can never delete. Constraint C1 closes it. Without C1, "creator" is not really the creator.

**Member who left.** Fail closed: nobody can delete or restore an expense whose payer is no longer a member (is_verified_trip_member fails for the payer; no organizer override per decision). Acceptable for v1, but document it as a known limit (a wrong entry by a departed member stays counted). Do NOT add an organizer override as a quiet fix; if wanted later it is a separate, audited feature. Also remove/leave must not become a way to dodge: a leaver's hidden expenses stay hidden and stay in export.

## Constraints (for design and implementation)

### Database enforcement (blocking if missing)
C1. Delete/restore only via a SECURITY DEFINER RPC pair (suggest `delete_expense(_expense_id)` and `restore_expense(_expense_id)`), each checking, inside the function: `auth.uid()` not null, `is_verified_trip_member(trip_id)` of the expense's own trip (derive trip_id from the expense row, never from a client param), `paid_by = auth.uid()`, `is_trip_open(trip_id)`. Raise a fixed code-only error otherwise. Also tighten the insert policy to `paid_by = auth.uid()` (both app paths already do this; the RPC already uses auth.uid()), so creator = payer is true at the database.
C2. SECURITY DEFINER hygiene: `set search_path = public` (or empty with fully-qualified names), `revoke execute ... from public, anon`, `grant ... to authenticated` only; no defaults on parameters; check `auth.uid() is not null` explicitly (anonymous sessions are `authenticated` role, so is_verified_trip_member is the real gate, and it must be what rejects unverified/anonymous-unlinked callers).
C3. Soft-delete column (`deleted_at timestamptz null`) must NOT be writable via the direct UPDATE path. Today the payer can update any column of their own open-trip expenses via PostgREST. Otherwise a payer can set `deleted_at` directly and strand a bought list item linked to a hidden expense (breaking atomicity, AC 10), or edit a hidden row, or restore without re-linking. Do one of: column-level `revoke update` on all columns then grant update only on amount/description/date (and keep paid_by/trip_id immutable); or a BEFORE UPDATE trigger that rejects changes to `deleted_at`, `paid_by`, `trip_id` unless made by the RPC; or add `deleted_at is null` to the UPDATE policy `using` and the WITH CHECK `deleted_at is null` plus the trigger for restore. Must be tested directly via the `authenticated` role, not only via the RPC.
C4. Remove the hard-delete path. Drop the `"members can delete expenses"` DELETE policy (any verified member can today hard-delete any unlinked expense on an open trip; the FK blocks only linked ones). AC 7 and 9 require this; test that a direct `DELETE` as payer, as other member, and as non-member affects 0 rows. Add no DELETE policy at all.
C5. Atomicity: delete and restore each update the expense and the linked `shopping_list_items` rows in one function body (one transaction). On delete: `update shopping_list_items set status='claimed', expense_id=null where expense_id = _id` (claimed_by is preserved for logged rows, so the shape check holds; confirm and test, including the case where claimed_by was nulled by member removal: that row would violate the shape check on revert, so set status='open' when claimed_by is null). On restore: re-link only rows that this expense previously held. Because delete clears `expense_id`, the design needs a way to know which items to re-link (e.g. a `shopping_list_items.deleted_expense_id` or storing the item ids); that is a new column and is subject to C7/C8. Do not re-link by matching description.
C6. Restore race (D2): the re-link `update` must be conditional (`status='claimed' and claimed_by = <caller's member id> and expense_id is null`), taken under row lock (`for update`) to avoid two concurrent restores/claims; compare counts; restore the expense regardless and return a code (not a message from the database) saying how many items could not be re-linked. Idempotence: delete of an already-deleted row and restore of a non-deleted row must be a no-op or fixed error, never double-apply, never error with row content.
C7. New columns: `deleted_at` needs a database-side shape guarantee where applicable (nullable timestamp, no free text). Do not add `deleted_by`/audit text (user decision). If a new FK column is added to shopping_list_items, add the index and a CHECK keeping the existing shape constraint valid.
C8. Migration safety: new numbered migration (next after 0023), additive `add column deleted_at ... null` (no default rewrite, no NOT NULL, metadata-only on populated tables), idempotent DDL (`if not exists`, `drop policy if exists`; 0022 needed this fix). Safe with old code + new schema: old code reads all rows, so deleted rows would show up in old clients until new code deploys; since nothing writes `deleted_at` until the RPC is called by new code, this is safe if the RPC and UI ship together. New code + old schema: UI must treat PGRST202/42883 as "delete unavailable", not retry via direct DELETE. Narrowing the DELETE policy is safe for old code (no UI ever deleted). Policy changes done in one transaction. Test on a local scratch Postgres seeded with existing rows (expenses with and without linked items, completed and open trips, a removed-member payer); never against the live or .env.local project.
C9. Do not let a policy/RPC rewrite regress existing gates: `is_trip_open` use on insert/update stays; `add_expense_and_log_shopping_items` stays callable and must refuse nothing new; its insert must not set `deleted_at`.

### Every read path excludes deleted rows (blocking if missed)
C10. Default to excluding at the database where possible: make the SELECT RLS policy `"members can read expenses"` hide deleted rows from everyone, and expose the creator's own hidden rows only via a dedicated narrow read (the D1 "Recently deleted" list), e.g. a `list_my_deleted_expenses(_trip_id)` RPC returning only id, description, amount, date for `paid_by = auth.uid()`. This is safer than relying on every `.select()` adding `deleted_at is null`: a missed query then fails closed. If the architect instead keeps RLS unchanged, the following must each add the filter and each needs a test: `getTripView`, `getMyTrips`, `get_trip_summary` (0016, SECURITY DEFINER, bypasses RLS so it MUST filter itself in total and per-member paid), `edit-expense-sheet-content.tsx` single-row read (deleted must look like not-found), the shopping-list "Bought" link target, and any new RPC added later. Add a test that greps the codebase for `from("expenses")` and `public.expenses` in SQL and fails on any not on an allowlist.
C11. Hidden rows remain readable to every trip member through the API if RLS is not changed (description is free text and may be personal). State this accurately in the privacy copy decision; prefer C10 so it is not true.
C12. Where a hidden row must still count (deliberately), document why: `was_removed_from_trip` (0014) and the abandoned-anonymous purge (0018) should keep counting hidden rows (a payer with a hidden expense is still a participant; purge must not delete a user who has any expense row, including hidden, since `paid_by` has no ON DELETE action and the delete would fail). Hidden rows must NOT count in balances, totals, settlement, home totals, trip summary.
C13. Account export/deletion runbook: export includes hidden expenses the user paid (with a flag); erasure case A/B queries on `paid_by` already include them; update the runbook text. Retention (D5): keep with the trip, no timed purge in v1, accepted, but the privacy page/LEGAL_LAST_UPDATED must be reviewed; do not say "permanently deleted" or "erased" anywhere in UI.

### Client, errors, logging
C14. UI hides controls for non-payers/locked, but this is UX only. The caller id is never sent from the client; the RPC takes only the expense id. Validate it is a UUID server-side (Postgres uuid parameter type does this).
C15. Errors: wrap RPC errors into a code-only error (baseline: constraint `details` contains the row). Never display or log raw database errors, description or amount. No analytics properties with expense ids/description/amount; `trackEvent` name-only.
C16. No notifications, no "deleted by" (user decision); confirm no trigger/realtime/webhook is attached to `expenses`. If realtime subscriptions exist on expenses, check they do not broadcast hidden rows.
C17. Undo timer is client state only; Undo calls the same restore RPC (re-authorized server-side). Do not store the pending-undo in URLs/localStorage with expense data. A pending-action replay after an auth gate is not needed (delete requires a verified member).
C18. Rate/abuse: delete/restore toggling on one's own expense is bounded by RLS to own rows, but a loop could churn balances for the whole trip with no trail (no log by decision). Mitigation (should-fix): cap the delete/restore calls per user per trip per minute via the existing `rpc_rate_limits` mechanism, test the real path. Also accepted residual risk: a payer can silently remove their own expense on an open trip; compliance to confirm (open trips are not "locked/settled").

### Items 2 to 4 (Settle-up, Invite padding, Send feedback)
C19. Settle-up button removal: UI only; keep `complete_trip` server no-op on repeat (test). No new surface.
C20. Feedback link on You: `/feedback` must keep requiring a session (proxy); do not pass trip id or user data in the link/query. Unchanged copy and storage. Check anonymous users can still reach it only as today.
C21. Invite padding: no security impact.

## Blocking gaps in requirements.md (add as acceptance criteria)
B1. Requirements do not say that the direct DELETE policy is removed (AC 7 says "no longer works" but not that hard delete is gone entirely). Add: no hard-delete path exists for any role (C4).
B2. Requirements do not say direct UPDATE of the hide mark is blocked (C3). AC 6 refuses "delete and restore" at the database, but a payer can write `deleted_at` directly through the existing update policy, bypassing the atomic list-item step and AC 10. Add an AC for it.
B3. Nothing requires deleted rows to be hidden from a direct API read (AC 5/13 cover only the app). Decide C10 (preferred: RLS hides) or add an explicit statement of accepted exposure plus per-path tests.
B4. Creator = payer is not enforced at insert (C1). Add AC: an expense cannot be inserted with `paid_by` other than the caller.
B5. Restore re-link needs to know which items were linked; the design must record this (C5). Not a requirement gap per se, but AC 11 cannot be met without it, so flag for the architect.

Should-fix (not blocking): D1 "Recently deleted" must be visible only to the payer (C10); rate limit (C18); runbook and privacy text (C13); departed-payer limit documented (Positions).

Test requirement: all of C1 to C8, C10 must be exercised on a real local Postgres (as non-payer, unverified/anonymous, non-member, locked trip, deleted-twice, restored-twice, concurrent claim between delete and restore, item with claimed_by nulled by member removal) before QA passes.

# Revision 2 (2026-10-19): Undo-only, then hard erase (37-criteria requirements)

This section supersedes the earlier text wherever they conflict. Dropped as moot: C10's "creator's own hidden rows" read RPC (no Recently deleted), C11, C13, C12's hidden-row counting, B5 as a long-lived link (now only needed inside the window). Still in force: C1 to C9 (renumbered as criteria 16 to 24), C14 to C21, and positions on paid_by and departed payers (criterion 15, agreed).

Verified facts that drive this revision: pg_cron is optional in this repo (0018 and 0019 schedule only `if exists (select 1 from pg_extension where extname='pg_cron')`, otherwise just a notice). So a cron-only finalize can silently not exist. `shopping_list_items.expense_id` is a plain FK with no cascade, `expenses.paid_by` has no ON DELETE action, and `expenses.trip_id` cascades from trips.

## R2-1. Finalize/erase mechanism and its backstop
- F1. Correctness and privacy must not depend on erase timing. Any row with `deleted_at is not null` is hidden from every read path (RLS read policy `deleted_at is null`, `get_trip_summary` and the edit read filter it, balances exclude it) whether or not its window has expired. Erase is then only hygiene, so a late or missing finalize cannot resurrect or leak a row. Criterion 21 should say "any row with the deleted mark", not only "inside the window".
- F2. Layered finalize (the architect must pick at least two layers, because pg_cron is not guaranteed):
  1. Scheduled: pg_cron job every minute or less (same guarded pattern as 0018/0019, `unschedule` then `schedule` so re-apply is idempotent). If pg_cron is missing, the migration must not pass silently: raise a notice AND the runbook gets a check query ("count of rows with deleted_at older than N minutes", must be 0).
  2. Opportunistic: the delete and undo RPCs, and optionally one frequent read RPC, first erase expired rows in the same trip (bounded: `limit` e.g. 50, ordered, `for update skip locked`). This gives a backstop with no extra infrastructure for any trip that is still active.
  3. Optional authenticated RPC `finalize_expired_expenses(_trip_id)` is allowed only if it is expiry-gated (see F4). Do not make a client-called finalize the primary mechanism.
- F3. The architect states a maximum delay: with cron it is window + grace + cron period; without cron it is unbounded for an idle trip. Because F1 holds, an unbounded delay is a retention/hygiene problem, not a security one, but the runbook alert (F2.1) must exist. Add as a criterion: "maximum erase delay stated, and an operator check exists".
- F4. Finalize predicate, evaluated under the row lock, not from a prior read: `deleted_at is not null and deleted_at < clock_timestamp() - (undo_window + grace)`. Never `deleted_at is null`, never trusting a client-supplied time or id list. A test must prove finalize cannot delete a live row (deleted_at null), an in-window row, or a row of another trip, as any role. This is the single most important test in this feature, because the erase is irreversible with no audit trail.
- F5. Finalize function execute: revoke from public, anon and authenticated; grant only to the cron owner/postgres, and invoke it from the DEFINER delete/undo RPCs internally. If a member-callable wrapper exists it takes a trip id, verifies verified-membership, uses F4, and is rate limited (it can only erase rows that would be erased anyway, so the abuse is only cost; cap batch size).

## R2-2. Hard delete only inside the controlled path
- H1. `revoke delete on public.expenses from anon, authenticated` (privilege, not only policy) and drop the DELETE policy; add none. Do not use a BEFORE DELETE trigger to gate this, because trip and account cascades (`trips` on delete cascade, 0018 purge) legitimately delete expenses and must keep working. Test both: direct DELETE by payer/other member/non-member affects 0 rows or errors; deleting a trip still cascades; the purge still works.
- H2. Existing QA tests that delete expenses directly as a member must be updated, not worked around.
- H3. Finalize deletes expense rows only after list-item links are already cleared (done at delete time, criterion 8). The finalize must still defensively clear any `expense_id` pointing at the row inside the same statement/transaction so an FK violation can never block erase or strand a row (criterion 23). Any new "re-link" memory column on `shopping_list_items` (see R2-4) must be `references public.expenses(id) on delete set null` or be explicitly cleared by finalize, so erase leaves no dangling or blocking reference. A plain uuid with no FK is not acceptable (orphan).

## R2-3. Undo vs finalize races and the window
- U1. The window is defined and enforced only by the database clock (`clock_timestamp()` or `now()` in the RPC), never by the client timer. The UI timer is cosmetic.
- U2. Make the server's Undo window slightly longer than the UI's 10 s (e.g. Undo accepted until deleted_at + 15 s) and the erase eligibility later still (window + grace, e.g. >= 30 s). This prevents a tap at 9.9 s plus network latency from losing a race to a finalize, and removes clock-skew complaints. State the numbers in the architecture.
- U3. Undo and finalize both take the expense row lock (`select ... for update`). Whoever gets the lock first wins; the other re-evaluates and either finds no row (fixed code-only "not found/expired" error) or `deleted_at is null`. Under READ COMMITTED a finalize built as `delete ... where id in (select ... for update skip locked)` is safe; a plain `delete ... where deleted_at < x` can delete a row an Undo just cleared if the predicate is not rechecked, so the predicate must be rechecked after lock acquisition (Postgres does this for a single-statement DELETE with a WHERE, but verify with a two-session test, not by reasoning).
- U4. Delete of an already-deleted row restarts or not? Must not extend the window by repeated delete (a payer could keep a hidden expense indefinitely as a "soft hide"). Delete on a row that already has `deleted_at` is a fixed error/no-op and never rewrites `deleted_at`. Add to criterion 23.
- U5. Undo after erase must return the same fixed error as Undo after expiry (no distinguishing information about whether a row ever existed beyond what the caller already knew, and no row content).
- U6. Tests (real local Postgres, two concurrent sessions): undo at the boundary, finalize at the boundary, undo during finalize, double-undo, delete-undo-delete, and finalize run with no client at all (criterion 18).

## R2-4. List-item re-link on Undo
- L1. Delete transitions linked items atomically and records the link for Undo within the window (e.g. `shopping_list_items.unlinked_from_expense_id`, nullable, FK with `on delete set null`, index). Because items go back to claimed/open, record enough to verify "still in the state delete left it".
- L2. Undo re-links only rows where `unlinked_from_expense_id = _expense_id and expense_id is null and status in the state delete left it and claimed_by is the same member`, under lock, and clears the marker on every row that references the expense whether re-linked or not (so no stale marker survives to enable a later wrong re-link). Never match by description. Items not eligible are left untouched, silently (decision D2).
- L3. When another member claims, edits or deletes the item in the window, that action must also be consistent with the marker (claim/unclaim/delete-item RPCs should clear the marker or the Undo predicate must reject it). Test the concurrent claim case from the requirements.
- L4. Finalize clears markers (or the FK `set null` does) so no item keeps a pointer after erase.
- L5. Member removal trigger (`release_shopping_list_claims_on_member_removal`) must remain valid with the new column (claimed_by nulled for a logged/unlinked row must not violate the shape check; unchanged rule: `claimed` requires claimed_by not null, so an item whose claimer was removed returns to `open`, criterion 8). Re-test the trigger.

## R2-5. Trip lock inside the window
- T1. Delete and Undo both require `is_trip_open`. A row deleted before lock stays excluded from balances, so the locked settlement equals what members saw (consistent), Undo is refused, and finalize still erases it (criterion 23). Security view: acceptable, since erasing after lock does not change any visible amount (the row was already excluded); the alternative (blocking finalize on a locked trip) would leave a hidden row forever, defeating the decision.
- T2. A race between `complete_trip` and Undo must not allow Undo to succeed after the trip is locked: Undo checks `is_trip_open` inside the same transaction after taking the row lock; `complete_trip` ordering means the worst case is Undo winning just before lock (settlement then includes the expense), which is legitimate. Test that Undo after lock is refused.
- T3. The lock is the compliance control for "settled amounts are never silently changed". Make sure the opportunistic finalize and cron do not require `is_trip_open` and do not touch live rows of a locked trip (F4).

## R2-6. RLS hiding during the window
- S1. Read policy: `is_trip_member(trip_id) and deleted_at is null`. No creator-only visibility is needed any more (the client keeps the expense in memory for the toast; Undo takes only the id). This also means a payer cannot read their own deleted row via the API; acceptable.
- S2. UPDATE policy `using`/`with check` must include `deleted_at is null` (and the column deleted_at, paid_by, trip_id must not be changeable by direct update: column-level grants or a trigger). Existing risk (earlier C3) stays: a payer can otherwise write `deleted_at` directly through PostgREST, skipping the list-item step and (worse now) skipping the controlled path to a hard erase. With cron/opportunistic finalize erasing any expired `deleted_at`, a direct write of `deleted_at = now() - interval '1 day'` by the payer would be a way to trigger erase with no RPC checks, which is exactly criterion 19's "members cannot erase before the window". So criterion 20 is a hard requirement, tested directly as authenticated and anonymous.
- S3. `deleted_at` value is written only by the RPC from the DB clock; add a CHECK `deleted_at is null or deleted_at <= now() + interval '1 minute'` is not needed, but forbid direct writes (S2).
- S4. A SECURITY DEFINER view or function added later must filter `deleted_at is null`; keep the allowlist test (criterion 21). `get_trip_summary` filters total and per-member paid and returns no description.

## R2-7. Rate limit and abuse
- A1. Criterion 25 stays should-fix, but upgrade to must-have for finalize cost: delete/undo per user per trip per minute via `rpc_rate_limits`, tested on the real path (baseline: throttle bypass was found live). Delete-undo cycling churns everyone's balances with no trail; the cap bounds it. Also cap the opportunistic finalize batch (F2).
- A2. Residual risk to be accepted by compliance: a payer can irreversibly erase their own expense on an open trip after 10 s, with no record. Mitigated by creator-only, open-trip-only, explicit action. Record this in the design.

## R2-8. Migration safety
- M1. Additive nullable columns only (`expenses.deleted_at`, `shopping_list_items.unlinked_from_expense_id`), partial index `on expenses (deleted_at) where deleted_at is not null` so finalize does not scan the table. `if not exists` and `drop policy if exists` everywhere; wrap policy swaps in the one transaction so there is no moment with no UPDATE policy or an open DELETE policy.
- M2. Old code with new schema: old reads of `expenses` still work (RLS hides marked rows); no old code path writes deleted_at. New code with old schema: PGRST202/42883 means "delete unavailable", never a direct `.delete()` fallback (criterion 24). Order of deploy: schema first, then code.
- M3. Revoking DELETE and tightening insert affect old clients only for non-app direct API calls.
- M4. The cron registration is inside a guarded DO block, idempotent on re-apply (unschedule if present), and its failure does not fail the migration; the notice plus runbook check covers it.
- M5. Interaction with 0018 purge and account deletion: both fail or skip while a row exists inside its window (paid_by has no ON DELETE action). Test: account deletion during the window either waits or succeeds, never orphans, and the cron job does not keep a deleted-account's row forever (finalize erases it, then deletion proceeds).
- M6. Test on a scratch local Postgres seeded with existing rows (linked and unlinked items, open and locked trips, a removed-member payer), including the cron-absent path. Not against the live database.

## Blocking gaps in the 37 criteria (criteria changes needed)
All earlier blockers B1 to B4 are addressed by criteria 19, 20, 21, 22. B5 is addressed by criterion 8. New or remaining items:

N1 (blocking). Criterion 18/21: hiding must not depend on finalize. Reword 21 to hide any row with the deleted mark (expired or not), and add: "a row whose erase is delayed or never runs is still invisible to every read path and cannot be undone after the window." Without this, a missing pg_cron (which this repo explicitly tolerates) leaves hidden-but-present data indefinitely and Undo semantics ambiguous.
N2 (blocking). Criterion 18: add that the backstop does not rely on a single optional extension. Require at least two layers (scheduled and opportunistic in-RPC), the stated maximum delay, an operator check query in the runbook, and a test of the cron-absent path.
N3 (blocking). Criterion 19/20: state the predicate. Finalize erases only rows with the deleted mark whose window plus grace has passed, evaluated under row lock; no caller-supplied time or id list; test that it cannot delete a live, in-window or other-trip row; the table privilege DELETE is revoked from anon and authenticated (not just the policy).
N4 (blocking). Criterion 17/23: the window is defined by the database clock; Undo window slightly longer than the 10 s UI window and erase later than Undo; two-session boundary race tests; repeated delete never extends or rewrites the window (U4).
N5 (should-fix, likely blocking for QA). Criterion 8/9: the re-link memory must have a defined representation that is cleared on Undo, on finalize and on any intervening item change, with no dangling reference (L1 to L5); the criteria only say "the design records which items were linked".
N6 (should-fix). Criterion 25: promote to must-have, include finalize batch cap.
N7 (note). Criterion 28: confirm with compliance that an irreversible erase with no audit trail is acceptable; security sees it as acceptable only under creator-only, open-trip-only, Undo and rate limit (A2).

# Design review (2026-10-19, design mode)

Reviewed: architecture.md, design.md, ADR 0017, the architect's edits to security-baseline.md, against Revision 2 (F, U, L, T, S, A, M and N1 to N6) and the earlier C-list. SQL claims were sanity-checked on a scratch Postgres 10.5 in the scratchpad (stubbed `auth.uid()`, roles `anon`/`authenticated`, tables reduced to the relevant columns; stopped afterwards). Policy names were checked against migrations 0001 to 0009 (not run).

Scratch results (all as expected by the design): `revoke update` plus `grant update (amount, description, date)` lets the payer update `amount` on a live own row and denies `deleted_at`, `paid_by` and `trip_id` with "permission denied" before RLS; direct DELETE is denied; a SELECT policy `deleted_at is null` hides the row from the client role; an UPDATE policy with `deleted_at is null` makes a hidden row update 0 rows; a `where deleted_at is null` clause in a client UPDATE needs no extra privilege; the erase pattern (`select ... order by deleted_at limit 50 for update skip locked` on a `clock_timestamp()` predicate, then item revert, then delete with `deleted_at is not null`) erased only the expired row. The two-session races and Supabase default privileges could not be reproduced here; QA must (see S3).

## Blocking gaps

B1. **The policy swap names the wrong policies.** The architecture says `drop policy if exists` then `create policy` but never names them. The live policies on `expenses` are the migration 0009 names, not the 0001/0005/0006 names: select `"owner or verified member can read expense detail"`, insert `"verified member can add expenses"`, update `"verified payer can edit their own expenses"`, delete `"verified member can delete expenses"`. Permissive policies are OR-ed: if 0024 drops a stale name (`if exists` silently does nothing) and adds a new policy beside the real one, the old select policy keeps exposing marked rows to every member, the old insert policy keeps allowing `paid_by <> auth.uid()`, and the old update policy keeps allowing update of a marked row. This defeats criteria 19 to 24 at the database while the TypeScript looks correct.
Attack: member A calls PostgREST `GET /expenses?trip_id=eq.X` after B deleted a row inside the window and still reads the hidden expense; or inserts an expense paid by B.
Fix: 0024 must drop exactly those four names (plus, defensively, the older names via `if exists`) and recreate under new names; the design must list the final policy set. Add a QA test that queries `pg_policies` for `public.expenses` and asserts the exact set: one select, one insert, one update, zero delete, each with the expected `qual`/`with_check` text containing `deleted_at is null` (and `paid_by = auth.uid()` on insert), so a surviving old policy fails the build. Add the same enumeration to the security baseline under the Migrations or Access control rules ("when replacing a policy, drop it by its live name and assert the full policy set").

No other blocking gap. Everything else below is should-fix.

## Should-fix

S1. **Design and architecture disagree on errors.** The architecture deliberately uses one code (EX001) for every delete failure so nothing distinguishes not-payer, locked, already deleted or missing. design.md 2.3 specifies separate copy for "not the payer", "trip locked in the meantime" and "already deleted: treated as success". The client cannot tell these apart from EX001, and must not be given a way to (that would re-add the oracle the architecture removed). Fix: one neutral line for EX001 (for example "Couldn't delete that expense. Refresh and try again."), the delete button disabled while the request is in flight to cover double taps; the locked state is shown from the already-loaded trip state, not from the error. Same for Undo (design 3.4 already uses one message). Also design 3.3 ("a new delete replaces the toast, the older one can no longer be undone") conflicts with architecture 6 (a list of pending entries); pick one. Either is safe at the database, but state it so the engineer and QA test the same behavior.
S2. Erase: re-assert the age in the delete itself (`and e.deleted_at < clock_timestamp() - public.expense_erase_after_interval()`), not only `deleted_at is not null`. The rows are locked so it is equivalent today; this is defense in depth for the irreversible statement against a future edit of the selecting query.
S3. QA must reproduce Supabase default ACLs on the scratch database (`alter default privileges ... grant execute on functions to anon, authenticated, service_role` and table grants to both roles) and then assert with `has_function_privilege`: `erase_expired_expenses`, `erase_expired_expenses_batch` and the two interval helpers are not executable by anon, authenticated or public; `delete_expense`/`undo_delete_expense` executable by authenticated only; `get_trip_summary` not executable by anon or authenticated after 0024 (guards against a `drop function` rewrite). Add a test that two sessions Undo vs erase at the boundary and a test that the policy set is exact (B1).
S4. The file wraps everything in explicit `begin; ... commit;`. Check how the migration is applied (hand-applied per the architecture, plus the Supabase CLI wrapping each file): an explicit `commit` is harmless in the SQL editor but can end the runner's own transaction early under some runners. Either keep it and state the apply method, or drop the explicit wrapper and rely on the single multi-statement call. Keep the cron block last with its own exception handler either way.
S5. Delete/Undo re-check payer and verified membership only before the trip lock. A member removed in the gap between steps 3 and 6 could still complete one delete. Harmless (they are the payer of their own row) but cheap to close: repeat `is_verified_trip_member` after taking the lock, or accept and note it.
S6. Note: `shopping_list_items.unlinked_from_expense_id` is returned by `select("*")` to members and points at an expense id they may not read. It carries no content; accepted.
S7. Note: the opportunistic erase is global (any trip) inside a user's delete/Undo. Accepted: it only erases rows already past the window, capped at 50, skip-locked, errors swallowed.

## Verdict
Design passes with one blocking item (B1, wrong policy names, with the exact fix above). After B1 and the criterion/test additions, no further security objection to starting implementation. B1 is a design-stage catch, not a missed earlier-mode item, but the baseline gets the "name policies exactly and assert the full set" rule.
