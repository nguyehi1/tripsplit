# Security constraints: account-deletion-self-service

Mode: requirements review (stage 4). Date: 2026-10-21. Reviewed: [requirements.md](../../../../features/account-deletion-self-service/requirements.md), [planning.md](../../../../features/account-deletion-self-service/planning.md), the [security baseline](../../project/security-baseline.md), the [delete-an-account runbook](../../../../runbooks/delete-an-account.md), `src/lib/supabase/service.ts` and its call sites, `src/app/you/page.tsx`, `src/lib/rate-limit.ts`, `src/proxy.ts`, and migrations 0001, 0009, 0010, 0013, 0014, 0015, 0018, 0024. No implementation exists. Nothing here is an exploitable finding in shipped code, so this file is safe to commit. The compliance side is in [compliance-constraints.md](compliance-constraints.md).

Verdict: **do not approve requirements as written.** Two blocking gaps (B1, B2) and one factual error to correct (B3). Everything else is a constraint the pm can add as acceptance criteria.

## Blocking gaps in the requirements

**B1. "Case A has no expenses, so no balance changes by construction" is false.** Shares are the equal split over current members ([data model](../../../../reference/data-model.md)). Criterion 2 only looks at expenses the user paid and trips the user created. A user who is a plain member of someone else's trip, paid nothing, but where others paid expenses, still sits in the denominator. Deleting the account deletes the member row (cascade) and silently changes every other member's share. On a completed trip the roster is locked on purpose (`remove_trip_member` and `leave_trip` refuse on a locked trip, migration 0014), so account deletion would become the one way around that lock and would alter a settled trip's balances. Same hole exists in runbook case A and migration 0018's purge (the purge is a policy choice for abandoned guests, but self-service is a user-triggered path with a stricter bar, compliance rule M1 spirit). Fix needed: eligibility must also refuse when the user is a non-creator member of a completed (locked) trip that has any expense. Requirements must also state the decision for open trips: leaving an open trip with expenses already shrinks the split for the leaver's own choice today (`leave_trip`), so allowing it is consistent, but the screen and `/privacy` must say that remaining members' shares on trips they were in will change. Recommended default: refuse (route to Request deletion) for any trip with at least one expense that has other members, open or locked, so deletion never changes anyone's number; the user can use Leave trip first on open trips. Either way the requirement must be explicit, and criterion 13's test list needs "plain member of another's completed trip with expenses" and "plain member of another's open trip with expenses".

**B2. No re-authentication requirement (open question 1 and 5).** See the answers below. A stolen or borrowed unlocked phone with a live session can irreversibly erase the account with only a typed word, which an attacker can read from the screen. This must become an acceptance criterion, enforced in the database, not an open question with a "no" default.

**B3. Factual error: this is not the second service-role call site.** `createServiceClient` is already used by `src/app/api/trip-invite/[code]/route.ts` and by `src/app/trip/[id]/page.tsx` (`getTripSummary`, migration 0021). It would be the third. The docblock in `src/lib/supabase/service.ts` ("exactly one call site") is also stale. Correct the requirements, the planning-derived wording and criterion 15. More important, the design should not need the service-role key at all (constraint C1).

## Constraints

Mapping: "AC n" is an existing acceptance criterion; "NEW" is a criterion to add.

### Authorization and where the logic lives

**C1 (must, supersedes AC 15 wording; NEW).** Implement the erase as one `SECURITY DEFINER` Postgres function called by the signed-in user's own session (`authenticated` role), with no user-id parameter: it reads `auth.uid()`. Do not introduce a service-role call. Rationale: the function can delete from `auth.users` directly (the 0018 purge already does, so cascades through sessions, refresh tokens and identities are proven); the eligibility check, the erase and the lock are then one transaction (AC 14) with no Admin-API half-state (AC 10), no third service-role call site, and no client-supplied id at any layer (AC 4). If the architect nonetheless wants the Admin API, it is a documented exception: the function takes the uid, is revoked from `public, anon, authenticated` and granted to `service_role` only, the server action derives the uid from `supabase.auth.getUser()` (not `getSession()`, not a cookie field, not a form field), and C3 to C7 still hold inside the function.

**C2 (must; AC 1, 7, 13).** The function re-derives identity eligibility from the `auth.users` row, never from the JWT alone (a stale or minted-before-upgrade token carries old claims): `is_anonymous = false`, `email is not null`, `email_confirmed_at is not null`. Any failure raises one fixed code-only error (new SQLSTATE like the `EX001` pattern in 0024, no message detail) identical for anonymous, unverified, ineligible and "no such user", so the function is not an existence or reason oracle on the erase path. Execute: `revoke ... from public, anon`, `grant ... to authenticated`, and test as `anon`, as an anonymous-session `authenticated` token, as an unverified user and as a verified user.

**C3 (must; AC 4, 13).** Server action or RPC must not accept a user id, email, trip id or "force" flag. The only inputs are the confirmation word (C8) and, if used, nothing else. Test that an organizer removing a member (`remove_trip_member`) and every existing RPC never touches `auth.users` (AC 4 test, kept).

### Atomicity and races

**C4 (must; AC 12, 14).** Inside the function, in this order: (1) throttle (C9), (2) `select ... from public.trips where created_by = auth.uid() for update` to lock every trip the user created (conflicts with `FOR KEY SHARE` taken by a concurrent `join_trip` or placeholder insert, and `add_placeholder` already locks the trip row `FOR UPDATE`, migration 0010), (3) only after the lock, run the eligibility queries as separate statements (under READ COMMITTED each statement gets a fresh snapshot, so a joiner who committed before the lock is seen, and a joiner arriving later blocks on the FK and then fails because the trip is gone), (4) delete the `auth.users` row, (5) assert the delete affected exactly one row. The `expenses.paid_by` foreign key (no ON DELETE action) is the last-resort backstop: a concurrent expense insert makes the delete fail with 23503, which must be mapped to the same code-only error, never forwarded (baseline: constraint `details` carry the row). Document the lock order and add a test with two real connections: join racing delete, add-placeholder racing delete, add-expense racing delete (solo trip, same user), and two simultaneous deletes. A second delete after the first commits finds no user and returns the fixed error (AC 12).

**C5 (must; AC 3, 13).** The "paid anything" and "trip has any expense" checks run inside the definer function and therefore bypass RLS, so they naturally include rows with `deleted_at is not null`. Keep it that way: do not reuse a view or RPC that applies the read policy. If every blocking expense is soft-deleted and not yet erased, return a distinct retry-soon code to the screen (AC 3). Do not call `erase_expired_expenses` from this path.

**C6 (must; AC 2, 13, B1).** Eligibility is a single SQL predicate, shared by the status RPC (screen) and the erase function so the two cannot drift; the erase function does not trust the status result. Counts the user's membership in trips created by others per B1. Placeholders count as other members (AC 2 and Q3 default).

### Recency of authentication (answers open questions 1 and 5)

**C7 (must; NEW, replaces the open-question defaults).** Require a recent sign-in, enforced in the function: `auth.users.last_sign_in_at > now() - interval '10 minutes'` (this column changes on sign-in through the email link, not on token refresh, unlike the JWT `iat`). If stale, the function raises a distinct "reauth required" code, and the screen offers "Send me a sign-in link to confirm" using the existing sign-in link flow, returning to `/you` (fixed path, no query parameter carrying intent; no pending-action replay is needed because after the link the recency check passes and the user taps Delete again). A typed word alone, or "verified email" alone, is not enough.

**Answer to open question 1: yes, require re-sign-in.** Firm recommendation. This is the first irreversible, user-triggered erase; the typed word is visible on screen and gives no protection against a person holding an unlocked phone, a shared family device, or a session cookie captured from a compromised browser. Signing in again requires the mailbox, which a phone thief usually lacks. Cost is one email per very rare action, which matches the stated frequency. It limits but does not eliminate the risk (an attacker with the mailbox open still wins); that residual is acceptable and should be stated in the design.

**Answer to open question 5: no, "verified" is not enough; verified email (C2) plus signed in within the last 10 minutes (C7).** The verified check proves the account is not a guest; it says nothing about who is holding the device now.

### Confirmation, CSRF, input

**C8 (must; AC 8).** The confirmation word is validated server-side (exact, case-sensitive match of the fixed word, passed as the function argument or checked in the action before the call). Say in the design that it guards against accidents, not attackers (C7 is the attacker control). Do not echo the submitted value in any response.

**C9 (must; AC 15, amended).** Rate limit per user inside Postgres with `throttle_rpc` keyed on `auth.uid()` (for example 5 per hour for the erase, a looser limit for the status RPC). Note the existing pattern's caveat: a call that raises rolls back its own increment (0024 comment), so the throttle on failing attempts needs either a non-raising "ineligible" return for the status call or placement that survives; the architect must say which and test the real direct-to-PostgREST path, not only the happy path (baseline: the 0013 bypass was found live). "Per IP-equivalent" in AC 15 is not achievable or meaningful when the call goes straight to PostgREST (Supabase does not overwrite `x-forwarded-for`, see `service.ts` docblock); change AC 15 to per-user, and add an app-level IP limit with `enforceRateLimit` only if a route handler is introduced. If the architect uses a server action or route anyway, add the Upstash limit as defence in depth and keep the Postgres one.

**C10 (must if a route or server action is used; NEW).** CSRF: a Next.js server action gets the framework's Origin-versus-Host check, which must not be weakened (no wildcard `allowedOrigins`; verify `next.config` before the design stage); a route handler gets none, so it must be `POST` only, require a JSON body, reject when `Origin` is absent or not the site origin, and check `Sec-Fetch-Site` is not `cross-site`. Never accept the action on `GET`. The RPC-from-browser design (C1) needs no CSRF token because it requires the user's bearer token in a header, which a cross-site form cannot set; note that as a reason to prefer it. Today the app has no server actions (`"use server"` appears nowhere), so there is no precedent to copy.

**C11 (must; AC 9, 10).** After success the response is a redirect to a static `/account-deleted` page that takes no parameters and reads no session (add it to the public list in `src/proxy.ts`; the proxy currently gates `/you`). The server clears the Supabase auth cookies itself and ignores errors from `signOut` (the user no longer exists, the call can fail). Note an access token minted before deletion stays cryptographically valid until it expires (up to an hour); verify with a test that it cannot do anything after the erase: the page-level `getUser()` call in `proxy.ts` rejects it because the user is gone, and any RLS check finds no membership rows. Record this in the design.

### Errors, logging, data exposure

**C12 (must; AC 11).** Map every outcome to a closed code set (`ok`, `not_eligible`, `reauth_required`, `retry_soon`, `rate_limited`, `unavailable`). No raw Postgres or auth error reaches the client, `console.error` or Vercel logs; log only the code and a static event name. No user id, email or trip id in logs, timing labels (`timeAsync` names), analytics, URLs or the `perf-log` route. Contrast with `trip-invite/[code]/route.ts`, which logs the caught error object: do not copy that pattern here.

**C13 (must; AC 5, 6).** The status RPC returns a closed enum of reasons only (`can_delete`, `anonymous`, `unverified`, `reauth_required`, `paid_expense`, `organizes_shared_trip`, `member_of_shared_trip_with_expenses`, `retry_soon`), never counts, names, trip ids or member names. It reads only the caller's own data via `auth.uid()`, is `authenticated`-only, and is throttled. If it is missing (new code, old schema) the screen fails closed to the Request deletion state and never shows the Delete button.

### Cascades and what remains

**C14 (must; AC 9, 16).** Retest on a real database that deleting the `auth.users` row removes: `trip_members` rows (including the BEFORE DELETE trigger from 0015 that nulls `added_by` / `claimed_by` before the member row goes, because `shopping_list_items.added_by` and `claimed_by` reference `trip_members(id)` with no ON DELETE action; this is the one path that could make the cascade fail for a plain member who added or claimed list items on someone else's trip, so test it explicitly), solo trips with `types` and `other_type`, shopping items on those trips, and `feedback` (`feedback.trip_id` is `on delete set null`, `user_id` cascades). Assert other users' rows are byte-for-byte unchanged. The 0018 purge must still run (AC 16).

**C15 (must; NEW, copy accuracy).** Decide and test what else holds the user id or email after the erase, and make `/privacy` literally true (compliance AC 18): `rpc_rate_limits` buckets are keyed on the uid text (`expense-change:<uid>:...`, and the new throttle key); the function should delete the user's own buckets in the same transaction (or the copy and the 0019 stale purge must be stated). Supabase's `auth.audit_log_entries` and platform logs can hold the email and IP; verify on a non-production project or with Supabase documentation whether hosted audit rows persist, and have the copy say "account, email, memberships, solo trips and feedback" without claiming logs or backups are erased (this matches AC 18's "no new backup claims"). Add a post-erase check query to the runbook for the operator.

### Migration and rollout

**C16 (must; AC 17).** One new numbered migration, additive only: new functions plus grants, no table rewrite, no policy changes, no edit of past migrations. Idempotent (`create or replace`, guarded grants). Every function parameter and variable `_v_`-prefixed to avoid the 0013 ambiguous-column failure (`users.email`, `trips.created_by`, `expenses.paid_by` collide with natural names). Explicit `revoke execute ... from public, anon` and a grant to `authenticated` (Supabase grants execute by default). Ship the migration before the code (new code + old schema fails closed per C13; old code + new schema is inert). No new overloads, so the PGRST202 fallback rule does not apply; treat PGRST202/42883 as `unavailable`.

**C17 (must; AC 13, 16, 17; test environment).** Test on a scratch local Postgres, never the project `.env.local` points at: `initdb` a cluster in the scratchpad directory, start it on a spare port (not 3000), stub `auth.users` (with `is_anonymous`, `email`, `email_confirmed_at`, `last_sign_in_at`), `auth.uid()`, `auth.jwt()` and the `anon`, `authenticated`, `service_role` roles, then apply migrations 0001 to the new one in order (existing `*.qa.test.ts` and `0024_*.test.ts` show the pattern). Required cases: payer; payer whose only expense is soft-deleted; organizer with another member; organizer with only a placeholder; organizer of a solo trip with an expense; plain member of another's open trip with expenses; plain member of another's completed trip with expenses; plain member who added and claimed list items; anonymous; unverified; stale sign-in; wrong confirmation word; call as `anon` and as an anonymous-session `authenticated`; direct call with a forged `request.jwt.claims` for a different user (must act only as that claim's uid, and never accept a parameter); two-connection races from C4; double submit; a policy and grant listing asserting the function's exact privileges.

### Other

**C18 (should; AC 21, 22).** The mailto links use fixed constants (subject and body) with `PRIVACY_EMAIL`; nothing from the URL, name or email is interpolated. The Request deletion link on the blocked screen is the only per-state difference, selected from the closed enum in C13.

**C19 (should; AC 24).** Extend the You page QA test with the three states and a test that the page payload (including the framework payload) for a signed-out or anonymous user does not contain the Delete control or any eligibility detail.

**C20 (note).** Anonymous-account 90-day purge relies on `pg_cron`, which is optional (baseline Migrations rule). The copy already says 90 days; not new, but the AC 7 text repeats the promise, so confirm the operator check query exists in the monitoring runbook.

- Amend AC 15 (no new service-role call site by default; per-user Postgres throttle; fix "second call site" to third if kept).
- Add: recent sign-in within 10 minutes enforced in the function (C7).
- Add: closed error code set and no ids in logs (C12), status enum (C13).
- Add: post-erase residue (rate-limit buckets, audit log) and exact copy (C15).
- Replace open questions 1 and 5 with the answers above; 2, 3, 4 defaults are acceptable.
